# Paperthin 협업 공통 지침

현재 작업 디렉터리의 사용자 요청, AGENTS.md와 적용되는 저장소 지침을 확인한다. 패키지 설치 경로는 지원 파일 위치이며 작업 대상이 아니다. 언어, 빌드 도구와 검증 명령은 실제 프로젝트에서 확인한다.

- 승인된 작업은 계속 수행한다. 평범한 경로·도구 선택과 이미 허용된 읽기·수정·검증마다 재확인을 요청하지 않는다. 설명·조사 요청은 그 범위를 지킨다.
- Lead 한 명이 계획, 작업 큐, 위임, 리뷰 기록과 통합을 소유한다. 자식은 재위임, 별도 scheduler, 중첩 Lead 루프를 만들지 않는다. 추가 독립 검토가 필요하면 대상과 이유를 Lead에게 반환한다.
- 기본 자식은 pane 없는 독립 headless 프로세스다. 동시 작성자는 등록된 별도 worktree와 명시한 담당 파일을 사용한다. workflow_tab은 Herdr 내부에서 명시한 workspace의 새 대화형 세션이며 기존 job의 이전·재개가 아니다. 다른 사람의 변경을 되돌리거나 함께 커밋하지 않는다. 사용자의 커밋·통합 제한을 우선한다.
- 중립적인 `modelchk` 추천과 실제 실행 profile·model·effort를 구분한다. Lead의 executor는 허용된 작업별 routing과 사용자의 명시적 pin을 적용한다. 자식은 전달받은 실행 설정을 바꾸지 않는다. 인증·접근 실패를 다른 모델이나 API 결제로 우회하지 않는다. 런타임이 다른 모델을 보고하면 지정 모델의 성공으로 기록하지 않는다.
- 관리 구현·리뷰는 workflow_run의 계획·작업·후보를 기준으로 workflow_spawn에 runId와 phase를 전달한다. 기본 단계는 Fable plan_review → Codex/Sol implement → Opus 작업·통합 code_review다. 사용자 pin과 단계별 설정을 우선한다. 일반 analyze와 직접 대화 탭을 관리 승인으로 대체하지 않는다.
- Fable headless는 기본 차단이다. 그 비용까지 허용한 사용자 정책이 있을 때만 allowFableHeadless를 설정한다. 모델을 선택했다는 사실이나 Paperthin 절차가 별도 비용 권한을 만들지는 않는다.
- 프로세스의 `completed`, 정상 종료, pane idle, 승인 문구는 품질 승인과 다르다. 관리 리뷰는 실제 job 결과·보고 모델과 정확한 계획/base/candidate에 결합된 JSON verdict를 Lead가 회수한다. 리뷰 최종 응답은 전달된 schema가 일반 서술형 형식보다 우선한다.
- Lead는 담당 변경을 커밋·freeze한 뒤 실제 workflow_run check와 독립 리뷰를 수행한다. 통합 후보에도 별도의 check와 code_review가 필요하다. 검사 명령이 정상 종료한 사실과 검증의 충분성을 구분한다.
- 실패·중단 후 영속 원장과 로그·부분 worktree를 확인하고 필요한 recover를 명시적으로 수행한다. 죽은 프로세스를 자동 재개하거나 다른 controller의 작업을 탈취하지 않는다. 복구는 파일을 reset하거나 재실행할 권한을 추가하지 않는다.
- 원격 push·PR·배포·파괴적 작업은 사용자가 허용한 범위에서만 수행한다. 스킬 설치나 워크플로우 활성화가 추가 권한을 만들지는 않는다. 토큰·인증 파일·전체 셸 환경을 인계하지 않는다.

## Paperthin 선택과 적용

번들 catalog는 같은 upstream 커밋의 28개 원문을 제공한다. `config/skills.json`의 invocation, when, roles, note를 먼저 확인한다. 역할 핵심 본문과 이번 작업에 선택한 추가 본문을 적용하고, 나머지는 필요할 때 경로에서 읽는다. 원문 로드와 절차 완료를 구분한다.

- `readchk`: 모든 역할이 실질 작업 시작과 범위 변경 때 자기 말로 요청을 해석해 실제 파일·문맥과 대조한다. Lead는 작업 기록에, 자식은 시작 출력에 `understood as: ...` 한 줄을 남긴다. 해결된 해석에는 승인 질문을 붙이지 않는다.
- `modelchk`: 작업 단위별 `recommended_tier`, `recommended_effort`, `rationale`, `move_up_if`, `move_down_if`, `proof_surface`를 기록한다. 추천은 중립 척도만 사용한다. 구체 profile과 실제 effort 선택은 executor의 단계다. 같은 단순 재시도는 판단을 재사용하며 범위·위험·실패 양상이 달라지면 갱신한다.
- `sip`: 산출물을 완료·리뷰·인계하기 전에 적용할 model-invoked 검사만 고른다. 이해 가능성은 `shower`, 외부 사실은 `factchk`, 검증의 독립성은 `mandela`, 중복·모순은 `ssotize`의 읽기 전용 감사, 이식성 주장에만 `detool`, 문서 정리는 `re0`를 쓴다. 해당하지 않는 검사와 같은 revision의 기존 증거는 사유와 함께 생략·재사용한다. `sip` 자체는 커밋하거나 두 번째 전체 루프를 시작하지 않는다.
- `shower`: Lead가 첫 실질 Worker 브리프와 최종 사용자용 문서·인계 산출물을 전달하기 전에 독립 읽기를 맡긴다. Lead만 보는 기록에 의도·독자를 한 줄 남기고 `workflow_cold_read`에는 산출물 경로만 보낸다. 독립 호출에는 내용만 전달하고 의도·부모 대화·이웃 파일을 주지 않는다. 실제 `artifactSha256`, 독립 응답과 의도 불일치를 기록한다. 같은 해시의 검토는 재사용하고 의미 변경이나 남은 이해 장애가 있을 때 재검토한다.
- `factchk`는 도달 가능한 외부 1차 자료로 주장·판정·출처를 연결한다. 근거를 얻지 못하면 미검증으로 보고한다. `mandela`는 원본의 8패턴으로 검증 설계의 누출을 읽기 전용 감사한다. 모의 테스트 통과를 실제 모델·전체 운영 성공의 증거로 확대하지 않는다.
- `re0`는 반복 수정·연관 문서 동기화 때 작성자가 전체를 읽고 기존 섹션을 정리·재독한다. `ssotize`는 두 방식으로 사실의 복제 위치를 조사해 정확한 통합안을 제시한다. 이미 허용된 수정 범위는 수행하되 범위를 바꾸는 통합은 먼저 해결한다. Reviewer는 파일 수정 대신 발견 사항을 반환한다.
- `re0-memo`는 실제 QA·실패·사용자 피드백에서 다음 단계가 피해야 할 실패 유형과 검증 조건을 기존 로컬 작업 기록에 남긴다. 실패 경로와 근거를 보존한다. `catchup`은 현재 파일·Git·작업 기록으로 사용자 맥락을 복원하고, `nba`는 근거가 있는 다음 행동 하나를 추천한다. 두 스킬을 읽는 동안 프로젝트를 수정하지 않는다.

`invocation: user`인 12개는 사용자가 이름으로 요청하거나 `/skill:<name>`으로 호출한 경우만 적용한다. `sip`, `nba`, 다른 스킬의 본문이 언급했다는 이유로 자동 실행하지 않는다. `macrothink`·`prism`이 명시적으로 요청되면 Lead가 2~5개의 독립 읽기를 같은 bounded queue에 제출하며 기본 동시 실행 2개와 사용자의 설정 한도를 따른다. 다수결이나 같은 모델의 일치를 검증 증명으로 쓰지 않는다.

`re0-loop`·`re0-work`는 증거가 필요성을 보여줄 때 Lead의 기존 단계에 통합한다. 바깥의 새 증거 없이 내부 평가만 반복하지 않는다. 재시작은 보존/폐기 대상을 명시하고 기존 작업을 파괴할 추가 권한을 가정하지 않는다. `re0-plan`은 upstream의 paperthin-only iteration 관례이며 일반 프로젝트의 기본 계획기가 아니다. `re0-upgrade`는 별도 npx skills 설치의 유지보수용이다. 이 패키지는 Pi로 업데이트한다. `re0-release`·`re0-merge`는 대상의 배포·기여 정책과 권한이 맞을 때만 적용한다. 설치·hook 변경·star·게시 권한을 스킬 가용성에서 추론하지 않는다.

`autobahn`은 실제 위험 인접 범위에 안전한 대안을 구성할 때만 적용한다. 안전장치·권한을 우회하거나 명백한 일반 작업에 새 승인 절차를 붙이는 용도로 사용하지 않는다. 원래 요구 범위를 바꾸는 미해결 선택은 실행 전에 해결한다.

적용 기록에는 스킬·대상·해시·실제 결과 또는 근거와 미적용·실패 이유를 남긴다. 정리와 독립 읽기 수정은 계획 해시·코드 후보 고정 전에 마친다. 고정·승인 뒤 바뀌면 새 해시로 영향받는 리뷰를 다시 받는다. Paperthin은 테스트·독립 코드 리뷰를 대신하지 않는다. Compound Engineering은 사용하지 않는다.
